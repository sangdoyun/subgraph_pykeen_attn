2️⃣ Problems When Deploying KG Embeddings on Mobile

Mobile devices introduce several constraints.


---

A. Memory Constraints

Typical mobile memory budget:

100MB – 500MB usable

But KG embeddings can explode.

Example:

Entities: 100k
Relations: 50
Embedding dim: 768

Memory:

100k × 768 × 4 bytes ≈ 300MB

Too large.


---

B. Compute Constraints

KG embedding inference involves:

vector operations

scoring functions

sometimes neural networks


Example scoring:

score(h,r,t) = ||h + r - t||

Even this becomes heavy if:

10k entities per query


---

C. Energy Consumption

Frequent:

embedding lookup

vector similarity

graph traversal


→ drains battery.


---

D. Incremental Updates

Your system continuously captures memory:

new event → new triple

Traditional KG embeddings require retraining.

Problem:

TransE retraining cost

Not feasible on-device.


---

E. Privacy

User personal knowledge graph contains:

contacts

locations

activities

conversations


Uploading KG to cloud → privacy concerns.

Hence some processing must remain on-device.


---

F. Latency

Agent interactions must be:

< 200 ms

Large embedding search slows down queries.

3️⃣ KG Embedding Methods You Can Use

Let's categorize methods by mobile suitability.


---

1️⃣ Translational Models (Best for Mobile)

These are lightweight.

TransE

Scoring:

h + r ≈ t

Advantages:

simple

fast

low compute


Good for:

mobile KG inference

small personal graphs



---

TransH

Improves TransE by projecting entities onto relation planes.

Better for:

multi-relational data


Still lightweight.


---

TransR

Separate relation spaces.

But heavier than TransE.


---

Recommended mobile choice:

TransE or TransH


---

2️⃣ Graph Neural Network Embeddings

Examples:

R-GCN

CompGCN

GraphSAGE


Advantages:

powerful reasoning

handles complex structure


Problems:

heavy computation

large memory


Not ideal for mobile inference.

Better for server pretraining.


---

3️⃣ Semantic KG Embeddings

Examples:

DistMult

ComplEx

RotatE


RotatE:

relation = rotation in complex space

Advantages:

handles symmetric relations

expressive


But slightly heavier than TransE.


---

4️⃣ Text + KG Embeddings

Useful for multimodal memory.

Examples:

KEPLER

KG-BERT

CoKE


But these use transformers → too heavy for mobile.

Better strategy:

server trains
mobile uses compressed embeddings

4️⃣ Modifications to the Architecture

To support mobile deployment, several improvements are needed.


---

1️⃣ Hierarchical Memory Graph

Instead of storing full KG on device.

Split memory:

Hot Memory (on-device)
Warm Memory (compressed)
Cold Memory (cloud)

Example:

Hot: last 7 days
Warm: last 3 months
Cold: archive

Only hot memory uses embeddings locally.


---

2️⃣ Subgraph Embedding Instead of Full KG

Rather than embedding entire graph:

embed user-centric subgraphs

Example:

User
 ├ friends
 ├ locations
 └ topics

This reduces embedding count.


---

3️⃣ Quantized Embeddings

Reduce memory.

Example:

float32 → int8

Memory reduction:

4x smaller

Techniques:

vector quantization

PQ (product quantization)



---

4️⃣ Dynamic Local Training

Instead of retraining KG model.

Use:

incremental embedding updates

Example:

For TransE:

new_entity = average(neighbor embeddings)

No retraining required.


---

5️⃣ Hybrid Retrieval Strategy

Use three stages:

Stage 1

Keyword filter.

Stage 2

Vector similarity.

Stage 3

Graph traversal.

This reduces expensive operations.


---

6️⃣ Edge + Cloud Hybrid KG

Architecture improvement:

Mobile:
    small KG
    embeddings
    fast retrieval

Cloud:
    full KG
    heavy reasoning

Sync periodically.


---

7️⃣ Temporal Graph Embeddings

Your architecture includes temporal reasoning.

Use models like:

Know-Evolve

TTransE

DyRep


But compute them offline, not on device.


---

8️⃣ Contextual Memory Compression

Cluster similar memories.

Example:

5 meetings with John

→ compress into

(User, frequently_meets, John)

This reduces graph size.
